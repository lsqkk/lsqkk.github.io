# 谍报风云（在线桌游）

4 人两队、用暗号互猜编号的实时桌游。访问路径：`/games/spy-signal/`，入口卡片登记在
`assets/pages/games/game.json` 的 `multiplayer` 分组。

## 1. 玩法要点

- 4 人分 A / B 两队（每队 2 人）。每队持有 4 个只有自己看得见的秘密词，编号 1–4。
- A 队先手，之后交替。每轮行动队派出**描述者 + 猜测者**，**对方整队担任监听方**。
  > 监听**不指派具体的人**：对方队伍任一成员都可以提交监听答案，谁先提交算谁的。
  > 早先是"必须指派一名监听者"，那个人一掉线本轮就彻底卡住，只能等房主作废；
  > 现在监听是"整队的事"，掉一个人也不影响继续（见 §13、§14）。
- 系统从 `[1,2,3,4]` 中不重复地抽 3 个编号作为**数字卡**（顺序随机），例如 `3-4-1`。
- 描述者看到「编号 → 自己的词」的对应关系，按卡片顺序为这 3 个词各写一条暗号。
- 暗号公开后：行动队猜测者与对方监听者各自提交一个 3 位编号序列；**数字卡此时仍然保密**。
- 结算（可叠加）：

  | 情况 | 行动队扣血 |
  |------|-----------|
  | 猜测者猜错 | −1 |
  | 猜测者猜对 | ±0 |
  | 对方监听者猜中 | −1 |
  | 对方监听者未猜中 | ±0 |

  因此"猜测者猜错 + 监听者猜中"= −2，一轮最多掉 2 血。
- 公开阶段公布数字卡与暗号的对应关系；对方队伍把这 3 条暗号按编号归档进**自己的情报板**
  （`teams[x].intel`），并可各自添加自定义笔记（同队两人可见）。
- **同一份"编号 → 暗号"也会归档进行动方自己**（`teams[x].clues`），显示在**我方词板每个词的下方**，
  逐轮列出"第 N 轮：<暗号>"。理由：连续两轮对同一个词给出语义相近的暗号，
  对方把两条线索并排一放就能锁定原词；以前想避开重复只能去翻回合日志，很容易忘。
- 任一队血量归零即结束，公开双方全部原始词汇、双方情报板与完整回合日志
  （结算屏的词板同样带各自的暗号史，方便复盘"哪一轮露了底"）。
- 房主「作废本轮」的那一轮**不扣血、也不写 intel / clues**（`reduceVoidRound` 只推进阶段与日志）。
  公开屏上原先写着"暗号已归档进对方情报板"，与实现不符，已改正。

> ⚠️ **公开阶段只公开"数字卡 ↔ 暗号"，绝不带出行动方的原词。**
> 原词只在对局结束（`phase === 'ended'`）时揭晓。这条是玩法核心：
> 监听者要靠情报板一轮轮逼近对方的词，每轮直接把答案摊开的话整个游戏就失效了。
> 代码层面的不变量是：**除自己队的词板、描述者自己的填写界面、以及结束屏之外，
> 任何地方都不得把 `teams[x].words` 渲染进 DOM**。改动 `views-*.js` 时请守住这条
> （E2E 里有对应的回归断言）。

初始血量默认 3，建房时可选 2–4；**开局前房主还能在房间里随时改**（`SET_HEALTH_MAX`）。

## 2. 身份与入口屏

### 身份

身份来源复用全站统一的 `assets/js/user-profile.js`（`window.QuarkUserProfile`），不另造一套：

- **已登录夸克博客**（GitHub OAuth 或站内账号）→ 直接用博客昵称与头像，入口屏只显示一行
  "已使用夸克博客登录身份"，不让人重复填。想换个名字对局时可以点「改用手动填写」。
- **未登录** → 显示"昵称 + 头像底色"表单。头像底色有 8 个预设色，昵称旁边实时预览首字头像。
- 选择记进 localStorage（`spySignalNickname` / `spySignalAvatarColor`），**下次进来免填**。
- 身份变化会即时跟上，不必手动刷新：`quark-user-updated`（站内模块派发）、
  `storage`（在另一个标签页登录 / 退出）、`visibilitychange`（从登录页切回来——
  `auth.astro` 是直接写 localStorage 的，不会派发事件）。

玩家 uid 优先取 `QuarkUserProfile.getUid()`（登录时是 `gh_xxx` / `qb_xxx`，未登录是持久化的
`quark_uid`），因此同一账号刷新、换标签页都还是同一个人；取不到才退回本页自己的
`spySignalUid`。

> ⚠️ **身份来源偏好只在用户显式点过"改用…"时才写入**（`spySignalIdentityPref`）。
> 早先版本在每次存档时都写入当前模式，于是"当时还没登录所以算出 manual"被当成用户的明确选择记了下来，
> 等真的登录了也一直停在手动表单上，看起来就是"登录了却读不到博客身份"。
> 现在改成：没有显式偏好时，每次加载都按当前登录状态重新判定。

> ⚠️ **昵称可能不等于 GitHub 用户名**：`user-profile.js` 的优先级是
> `localStorage.nickname`（站点全局显示名，评论等页面用）优先于登录昵称。
> 这是全站既有行为，游戏沿用不另立规则。

### 头像的可见范围

头像会显示给房间里其他人，所以入口做了校验（`game-core.js` 的 `sanitizeAvatar`）：

- **图片规则刻意与站点评论头像（`comment-input-shared.js`）保持一致**：
  `https` + 常见图片后缀（`.jpg` / `.jpeg` / `.png` / `.webp`）即可，
  另外额外放行 GitHub 这类"后缀看不出来"的固定域名
  （`avatars.githubusercontent.com` 等，其地址形如 `…/u/123?v=4`）。
  > 早先这里只允许四个白名单域名，结果把用户自己在站点里设置的头像（例如图床头像）
  > 也一并挡掉了，表现为"昵称同步了但没有头像"。游戏里再严格一套只会与站点不一致。
- 底色只接受合法的 3 / 6 位十六进制；任何不合规输入都安静地退回默认色。
- 渲染时用 `textContent` / 受校验的 `background-image` 写入，不拼 HTML。
- ⚠️ `avatar()` 部件要同时接受"房间玩家对象"（`avatarType`/`avatarColor`/`avatarUrl`）
  和"`sanitizeAvatar()` 返回值"（`type`/`color`/`url`）两种形状 —— 早先只认前者，
  博客头像传进去后字段名对不上，就静默退化成了首字圆圈。

### 入口屏结构

就两个按钮 —— **创建房间** / **加入房间**：

- 创建 → 点开对话框选初始血量（2 / 3 / 4）+ 创建
- 加入 → 点开对话框填房间码或邀请链接 + 加入，并列出最近加入过的房间
- **地址栏里带 `?room=` 时，第二个按钮直接进房、不弹对话框**，按钮文案也换成「加入邀请的房间」。
  房间码就写在提示里了，再让人在弹窗里看一遍同样的 6 个字符、再点一次「加入」纯属多此一举。
  想进别的房间时，提示里还有一个「换成别的房间码」的次要出口（打开对话框）。
- **加入时不再问"进哪一队"**：分队按人数自动补齐（人少的一队优先），
  进房后在大厅随时能换队（§13），加入时选一次没有意义。
  reducer 的 `JOIN` 仍接受 `payload.team`（`pickPreferredTeam`），只是界面不再发送它。

对话框用原生 `<dialog>` + `showModal()`，自带焦点陷阱、ESC 关闭与背景遮罩，不用手搓伪弹窗。
它渲染在独立的 `#ssModals` 容器里，而不是 `#ssScreens` —— 否则入口屏因昵称输入等原因重绘时，
对话框会被重建，正在输入的房间码会被清掉、焦点也会丢。

按钮本身**不套 `.ss-block` 外框**：按钮已经是明确的点击入口，再包一层框只是无意义的套娃
（遵循 `src/docs/UI/FlatUI.md`：一级结构可以有框，二级内容尽量不要再是框）。

> ⚠️ **原生 dialog 会让自定义光标消失**。本站的 `cursor-trail.js` 会注入
> `* { cursor: none !important }`，然后用一个 `z-index: 9999` 的元素当光标；
> 而原生 `<dialog>` 渲染在 **top layer**，层级高于任何 `z-index` ——
> 于是光标被对话框盖住、真实光标又是 `none`，整屏都看不见指针，只能盲点
> （站点自己的弹窗靠 `.popup-overlay * { cursor: auto !important }` 规避，是同一类问题）。
> 现在对话框打开期间会给 `<body>` 加 `ss-modal-open`，用
> `body.ss-modal-open * { cursor: auto !important }` 把原生光标还回来；
> 选择器带类名（0,1,0）能压过注入规则的 `*`（0,0,0）。**以后再引入原生 dialog / top-layer 元素都要注意这一点。**

## 4. ⚠️ 必须的 RTDB 规则

Firebase 安全规则是**顶层名字白名单**，新建命名空间默认会被 `PERMISSION_DENIED` 拒绝。
在 Firebase 控制台 → Realtime Database → 规则中，加一条与 `gomoku`、`quiz_battle` 同级的节点：

```json
{
  "rules": {
    "spy-signal": {
      ".read": true,
      ".write": true
    }
  }
}
```

只改一件事就能换命名空间：`assets/pages/games/spy-signal/rtdb.js` 里的 `ROOT_PATH`。
若以后不想让它平级，也可以退到已放行的 `rooms/` 下（改成 `rooms/spy-signal` 即可）。

> 注：规则是"无鉴权可读写"，这与站点其它小游戏（`gomoku` 等）一致。
> 界面上的"对方词汇不可见"是**客户端隐藏**，不是服务端鉴权——懂行的人可以直接读 RTDB。
> 这是个休闲桌游，故按现有站点惯例处理；若将来需要强隐私，需要改成服务端发牌 + 规则分级。

## 5. 数据模型

实际结构与最初设想的模型有两处刻意调整，都是为了贴合 RTDB 的脾气：

- 秘密词用 `{ "1": "老虎", ... }` 而非数组 —— 数组在 RTDB 里会因空洞/空数组被丢弃而变形，对象稳定得多。
- 线索用 `intel.{编号}.{roundKey}`、笔记用 `notes.{编号}.{pushId}` —— 追加即写新键，不需要读改写整个数组。
  `clues` 与 `intel` 形状完全一致，共用 `withArchivedClues()` 写入（一次结算同时写两处）。
- **`listenerId` 已从模型里删除**：监听不再是"某个人的角色"，而是"对方整队"（§13）。
  旧的房间数据带着 `listenerId` 也没关系 —— `normalizeTeam()` 不再读它，下一次事务写回时自然消失。

```text
spy-signal/rooms/{房间码}: {
  meta: { createdAt, hostId, healthMax, dealtAt, startedAt, endedAt,
          lastKick: { uid, name, by, reason: 'manual'|'timeout', at } | null },
  players: { [uid]: { name, team, role, ready, online, offlineAt, joinedAt,
                      avatarType: 'color'|'image', avatarColor, avatarUrl } },
  teams: {
    A: {
      words: { "1": "词", "2": "词", "3": "词", "4": "词" },
      intel: { "1": { "r2": "对方给的暗号" }, ... },   // A 对 B 编号的推断
      clues: { "1": { "r1": "我们给过的暗号" }, ... }, // A 自己给过的暗号（同一份映射的另一半）
      notes: { "1": { [noteId]: { text, by, name, at } }, ... },
      health, describerId, guesserId
    },
    B: { ... }
  },
  phase: 'lobby' | 'prepare' | 'select-role' | 'describing' | 'guessing' | 'reveal' | 'ended',
  turn: 'A' | 'B', round, currentCard: [n,n,n] | null, descriptions: [str,str,str] | null,
  guesses: { A: { seq, by, at } | null, B: ... },
  roundResult: { round, turn, card, descriptions, guesserGuess, listenerGuess,
                 guesserCorrect, listenerCorrect, healthLoss, healthAfter, voided, at } | null,
  logs: { "r1": RoundResult, "r2": ... },
  winner: 'A' | 'B' | null
}

// 聊天是房间节点的兄弟路径（理由见 §12）
spy-signal/chats/{房间码}/messages/{pushId}: { uid, name, text, at,
                                               avatarType, avatarColor, avatarUrl }
spy-signal/chats/{房间码}/teams/{A|B}/{pushId}: 同上，只自己队订阅
```

> ⚠️ 新加字段（`offlineAt`、`meta.lastKick`）**必须同时补进 `normalizeRoom()`**。
> `dispatch()` 交给 reducer 的是归一化结果，而 `commit()` 是 `{...room, ...patch}`，
> 没进归一化的字段会在下一次动作时被整个丢掉。

## 6. 并发模型（重要）

所有状态变更只有一条路径：

```text
客户端 → dispatch() → ref.transaction() → applyAction(room, action) → 提交
```

- **单一 reducer**：规则全部集中在 `room-model.js` 的 `applyAction`，纯函数、不改入参。
  动作在当前阶段非法就返回 `undefined`，事务被中止、原值保留。
- **由 RTDB 串行化**：扣血、换回合、归档线索都在同一次事务里读改写同一个房间节点，
  不会出现两个客户端同时结算导致状态错乱。
- **动作载荷里带随机值**：数字卡、发牌结果由客户端生成后放进 action，
  reducer 因此保持确定性（事务重试不会抽出另一副牌）。

### ⚠️ v8 `runTransaction` 的缓存坑

`dispatch()` 里有一处必须保留的写法：

```js
const keepWarm = () => {};
ref.on("value", keepWarm);          // ← 不能删
await ref.once("value");
const result = await ref.transaction(...);
ref.off("value", keepWarm);
```

原因是 `ref.once('value')` 在 v8 SDK 内部是"临时监听 → 取值 → 立刻移除监听"，
而 RTDB 的本地缓存按查询引用计数管理，移除监听会把刚取到的数据一起丢掉。
于是紧随其后的 `runTransaction()` 读到空缓存并认为"房间不存在"（`null`），
而 reducer 为了拒绝加入不存在的房间恰好会在 `null` 时中止事务 ——
表现为**"房间明明存在，别人却永远加不进来"**。建房不受影响，因为那里 `null` 本来就是正确答案，
所以这个问题很隐蔽。挂一个 no-op 监听器把节点钉在缓存里即可。
`createRoom` 之外的每个动作都要走这里，改动前请先跑 `npm run test:spy-signal`。

## 7. 房间生命周期与自动释放

玩家直接关标签页不会发出 `LEAVE`，所以除了"最后一人退出即删除"，还有按时间的兜底释放
（见 `rtdb.js` 的 `ROOM_TTL` / `roomRelease`）：

| 情形 | 释放时机 |
|------|---------|
| 最后一名玩家显式退出 | 立即删除房间节点 |
| 建房后一直没凑满 4 人（从未发牌） | 建房 15 分钟后，哪怕还有人挂着 |
| 对局已结束 | 结束 10 分钟后；若全员已离线则 3 分钟后 |
| 对局进行中但全员离线 | 最后活动 15 分钟后 |
| 座位为空 | 立即 |

清理由**任意一位在线玩家**顺手完成：进入页面后 3 秒扫一次，之后每 60 秒扫一次。
没有服务端定时任务，因此"房间一直被清理"依赖有人访问该页面；这符合站点无服务器的现状。

释放房间时会**连带删除它的聊天记录**（`clearChat()`）。聊天挂在 `spy-signal/chats/{房间码}`
这个兄弟路径下，房间没了它不会自己消失；"最后一人退出即删房"那条路也会由该客户端补一刀。

大厅 / 结束屏会显示释放倒计时提示。

## 8. 邀请链接

- 建房或加入后地址栏会变成 `?room={房间码}`，直接复制网址即可邀请。
- 顶栏房间码旁的 ⧉、房间屏与结算屏的「复制邀请链接」复制的都是这条完整网址。
- 别人打开带 `?room=` 的链接时：入口页显示邀请提示，**点一下按钮就直接进房**（不再弹对话框，
  也不再问"进哪一队"）。
  - 刻意不自动加入：昵称（未登录时）还等着填，先让人确认名字再进房，报错也才说得清。
  - 想进别的房间时用提示里的「换成别的房间码」打开对话框。
- 若链接指向的**正是自己上局的房间**（刷新场景），则直接恢复对局而不是回到入口页。
- 加入框同时接受三种写法，由 `extractRoomCode()` 统一解析：纯房间码、`?room=ABC123`、完整链接。
  是链接但没有 `room` 参数时会明确提示"这条链接里没有找到房间码"，而不是把整条链接当房间码。

> 房间码字母表是 `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`——**不含 I / O / 0 / 1**（避免口头或手抄读错）。
> 因此规范化时这些字符会被直接丢掉，而不是"猜"成别的字符。

## 11. 已知限制

- **隐私靠客户端**：对方词汇、数字卡的隐藏都在界面上实现，RTDB 数据本身是可读的。
- **没有服务端裁判**：数值都在客户端算，理论上可被篡改。角色权限（谁能提交）
  由 reducer 校验，能挡住误操作与并发冲突，但挡不住刻意伪造请求。
- **房间清理依赖有人访问页面**，无服务端定时任务。
- 未做观众位、观战、断线自动托管（描述者/猜测者掉线、或监听方整队离线时，
  由房主「作废本轮」继续；监听方只要还剩一人在线就能自己推进）。
- 聊天同样是**客户端隔离**：队内频道在结构上做到了"对方客户端不会下载"，但
  知道房间码的人仍可直接读 RTDB。和词汇隐藏是同一条底线。
  「描述/猜测阶段停用队内私聊」也属于同一层：它挡的是顺手说漏嘴，
  挡不住刻意绕开界面直接读 RTDB 的人。

## 12. 房间聊天室

右下角常驻一个圆形入口，点开是浮在页面上的聊天面板（**不是原生 `<dialog>`**，
理由见 §2 里那条 top-layer 会把自定义光标盖住的坑 —— 面板是 `position: fixed` +
`z-index: 70`，既低于光标的 9999，也不需要模态）。

两个频道，**各占一条独立的 RTDB 路径**：

| 频道 | 路径 | 谁能看到 |
|------|------|---------|
| 房间 | `spy-signal/chats/{房间码}/messages` | 4 个人 |
| 队内 | `spy-signal/chats/{房间码}/teams/{A\|B}` | 只有自己队 |

> ⚠️ 为什么聊天不放进房间节点（`rooms/{id}/chat`）？两条硬理由：
> ① `dispatch()` 把 `normalizeRoom(raw)` 交给 reducer，而 `commit()` 是 `{...room, ...patch}`
> —— 归一化结果里没有聊天字段，**任何一个对局动作都会把聊天记录整个抹掉**；
> ② 房间监听器挂在 `rooms/{id}` 上，聊天一旦在这个子树里，**每发一条消息都会触发一次整屏重绘**。
> 放在兄弟路径下，聊天有自己的监听器、也从不参与对局事务。
> `spy-signal` 顶层已在 Firebase 规则白名单内，子路径自动继承，**无需改控制台规则**。

- 队内频道分成两条路径而不是"一个列表加个频道字段"，是为了让"只队内可见"成为
  **结构上的保证**：客户端只订阅自己队伍的节点，对方队伍的消息压根不会进内存
  （与 `views-shared.js` 的 `visibleWords()` 同一个思路，E2E 有对应断言）。
  队伍归属在大厅可能变化，`chat.js` 的 `setTeam()` 会跟着退订 / 订阅，
  换队后原队伍的历史既不显示也不保留。
- 写入用 `push()`，**不走对局事务**；读取用 `limitToLast(60)`。
- **描述 / 猜测阶段队内频道停用**（`TEAM_CHAT_LOCKED_PHASES`，判据在 `game-core.js` 的
  `isTeamChatLocked()`）：这一刻描述者已经拿到数字卡，而他的队友正是要凭暗号还原数字卡的猜测者，
  队内频道只要能发言，"把 3-4-1 直接说出来"就比任何暗号都省事。
  对方队伍一并停用，免得留下"哪一队能私聊"这种需要解释的差别。公共频道不受影响 ——
  四个人都在场，说出去的话对手也听得到，不构成串通。
  - 界面：队内页签置灰上锁（按钮 `disabled`）并停在该页签的**公共**频道，面板上写明原因；
    控制器再判一道（`send()` 里的 `state.teamLocked`），绕过界面直接调也发不出去。
  - 状态由 `main.js` 在每次房间更新时 `chat.setTeamLocked()` 同步进来（它自己不读房间）。
    这个方法**不触发重绘**，因为调用方紧接着就会因为房间变化重绘一次。
- ⚠️ 发送表单必须**先清空输入框、再发送**。`onSend()` 一写出消息就会经 RTDB 回调触发
  `renderChat()`，而重绘会把输入框换成新节点（`withPreservedInputs` 还会把旧值搬过去）；
  发送之后才清的话，清到的是已经脱离文档的旧节点，新节点里那行字原封不动地留着
  —— 表现就是"发完还得手动删一次"。情报板笔记框（`ADD_NOTE`）是同一个坑，同样先清再派发。
- 但"先清再发"会带来另一个坑：**被拒的消息不该吞掉用户刚打的字**。
  于是两处都约定成"**先清 → 派发 → 失败就把草稿还回去**"：
  - `chat.send()` 返回**同步**的"是否受理"（未分队 / 队内已停用 / 被限流都是 `false`），
    这三种拒绝都不会写出任何东西、也就不会重绘，视图直接把草稿写回同一个输入框即可；
    真正的写入仍是异步的，写失败只 toast，不再把内容塞回输入框。
  - `ctx.act()` 返回 `Promise<boolean>`（事务是否提交），笔记框 `.then` 里失败时
    **按 id 重新取节点**再把文字写回去（那期间可能已经整屏重绘过，拿旧节点写等于白写）。
- 客户端限流 700ms（`CHAT_MIN_INTERVAL_MS`），文本走 `sanitizeChatText()`（`CHAT_MAX = 120`）。
  截断按**码点**而不是 UTF-16 单元 —— `slice()` 数的是 UTF-16 单元，emoji 正好卡在边界上会被劈成半个字符，
  存进去再渲染出来对四个人都是乱码（`sanitizeText()` 统一按码点截，昵称 / 暗号 / 笔记一并受益）。
- 未读红点只在"面板没开着这个频道、或窗口不在前台"时累加；打开 / 切到该频道即清零。
  历史消息（首次订阅拿到的 60 条）不算未读、不响铃。
- 面板顶部是可折叠的**聊天注意事项**（默认展开），文案在 `views-chat.js` 的
  `ROOM_NOTICE` / `TEAM_NOTICE`；要点是别发个人信息、别刷屏、**别用聊天报自己的秘密词或编号答案**。

## 13. 队伍与角色

### 分队

- 加入时**不再问"进哪一队"**：一律按人数补齐（人少的一队优先，`pickBalancedTeam`）。
  reducer 的 `JOIN` 仍接受 `payload.team`（`pickPreferredTeam`：该队没满就用它），
  只是界面不再发送 —— 进房后在下面这个入口换队只要一步，加入时多问一次没有意义。
- 大厅里自己那一行有「换到 X 队」（`SWITCH_TEAM`），目标队有空位才能换；
  换队会清掉自己的准备状态与双方角色槽（人都换队了，旧指派不再成立）。
  只动席位：词板与血量按队归属，所以不必重新发牌。
- **不变量：4 人满员时两队必然是 2 : 2** —— 加入只会落到没满的那队，
  而 2 : 2 时两队都满，任何换队都会被拒。所以不需要"自动平衡"这类补救按钮。
- 重连（刷新 / 换标签页）走 `reduceJoin` 的重连分支，**队伍原样保留**，即使请求里带了别的队。
- 对局开始后（`select-role` 起）不再接受加入、换队与移出。

### 角色：只有行动队需要指派

| 角色 | 谁来做 | 怎么定 |
|------|--------|--------|
| 描述者 | 行动队 | 本队指派（或「自动轮换本队角色」） |
| 猜测者 | 行动队 | 同上，**不能和描述者同一人** |
| 监听 | **对方整队** | 不用指派：`guessing` 阶段任一成员都能提交，谁先提交算谁的 |

- 因此 `select-role` 阶段**只有行动队有事可做**：对方那一屏是纯粹的等待说明。
  行动队两人一就位就 `tryBeginDescribing()` 直接进入描述阶段，不再等对方"派人监听"。
- `teams[x].listenerId` 字段已从模型、`clearRoles()`、`normalizeTeam()`、`currentRoles()` 里删除；
  `currentRoles()` 现在只返回 `{ describerId, guesserId }`。
- 角色条第三格显示的是「监听者 · B 队任一人」（占位圈写 2 人），而不是某个玩家的头像。
- `guessSideOf(room, uid)` 与 `reduceGuess()` 两侧**刻意不对称**：
  - 行动队：只有被指派的猜测者本人能提交（本队另一人是描述者，他已经知道答案）；
  - 监听方：`room.players[uid].team === otherTeam(room.turn)` 即可提交，
    `room.guesses[side]` 一旦有值，队友再来就会被拒（`GUESS` 现在有对应的拒绝提示文案）。
  - 提交后界面要**分清是不是自己提交的**：监听方两人共用一个答案，
    队友先交了的时候要显示"队友 X 已提交本轮的监听答案 …"，
    以前一律写"你已提交"，让人以为自己点过。
- 「作废本轮」的触发条件：`hostVoidRow` 检查**描述者/猜测者掉线**、**席位空缺**，
  或**监听方整队都没人在线**（只要还剩一个在线，本轮就还能继续）。
  > ⚠️ **"席位空缺"这一条是必须的**：对局中途有人点「退出」时，`reduceLeave()` 会
  > `clearRoles()` 但**保留当前阶段**，于是 `describerId` / `guesserId` 变成 `null`，
  > 场上再没有人能描述或提交猜测。早先这里只判断"在座的人是不是离线"，
  > 槽位为空时既不报 blocker、监听方又还有人在线，按钮就永远不出现 ——
  > 本轮彻底卡死，而且房间的闲置 TTL 要求全员离线，连自动释放都等不到。
  > `chat-smoke.mjs` 的 `[7]` 就是这个场景的回归用例。

## 14. 掉线、倒计时与移出

- 在线状态仍然是 `bindPresence()` **直接写** `players/{uid}` 的子节点（不走事务，
  因为 `onDisconnect` 没法派发动作）。断线时一次 `update` 同时写
  `online: false` 与 `offlineAt: ServerValue.TIMESTAMP`；重连后写回 `online: true, offlineAt: null`。
  用**服务端时间**是为了让所有客户端算出同一个倒计时。
- 界面在大厅 / 准备阶段显示 `离线 1:23 后移出`，倒计时由**每秒改一个文本节点**实现
  （`#ssOffline-{uid}`），不是每秒重绘整屏 —— 否则比原来的"抖动"还晃眼。
- 移出（`KICK`）分两种来源，权限刻意不同：
  - `reason: "manual"`（房主点「移出」）→ 只有房主可以，且只能移出**离线**的人，
    也不能移出自己（房主想走会自己点「退出」）；
  - `reason: "timeout"`（离线超过 `OFFLINE_KICK_MS = 2 分钟`）→ **任何在场玩家**都可以代发。
    后者必须"谁都能做"，否则房主自己掉线后就永远没人能把他挪走，剩下的人既开不了局也换不了人。
    多人同时扫到同一个目标没关系：事务串行化后只有第一个生效，其余因为"目标已不在座"自动中止
    （所以这条巡检派发时是 `silent` 的，不会弹出吓人的失败提示）。
- 「离线满 2 分钟」这条规则**由 reducer 兜住**，不只靠界面上的巡检：巡检跑在各客户端的时钟上，
  时钟偏一点就可能把刚掉线的人当成超时；reducer 是所有客户端都同意的那一层，那里再卡一道，
  保证**不会有人被提前移出**（宁可晚，不可早）。规则是：`reason: "timeout"` 时必须有 `offlineAt`，
  且 `Date.now() - offlineAt >= OFFLINE_KICK_MS`；不满足就中止事务 ——
  时钟偏慢的客户端会被拒、10 秒后巡检再试，偏快的则因为自己那道也被同一时钟卡住而不会提前动手。
- 巡检（`sweepOffline()`）在房间更新时 + 每 10 秒各跑一次，**一次只移出一个人**，
  并留 3 秒宽限吸收残余偏差。
- **时钟基准**：`offlineAt` 是服务端时间写的，所以比较也用服务器时钟 ——
  `rtdb.js` 订阅 `.info/serverTimeOffset` 并导出 `serverNow()`，巡检、倒计时、reducer
  统一走它（拿不到偏移时自然退回本机时间）。顶栏那条"离线 2 分钟"的说明文案也从
  `OFFLINE_KICK_MS` 算出来，不在 prose 里另写一个数字。
- **房主转移**：房主不在座时（退出或被移出），`meta.hostId` 交给剩余成员中 `joinedAt` 最早的那位。
  以前没有这一步 —— 房主在大厅一退出，剩下三个人**谁都点不动「开始游戏」**。
- 被移出的人会看到 `meta.lastKick` 写下的原因（"离线超过 2 分钟"或"被房主移出"）并被弹回入口屏。
- ⚠️ 客户端被强杀时 RTDB 要等心跳超时（通常 ≤60s）才发现断线，所以倒计时的实际起点
  可能比"关掉页面那一刻"晚半分钟左右。
- ⚠️ `bindPresence` 的写入是**先于 JOIN 也有可能**（被移出的客户端重连时又会写回来），
  会给 `players` 留下一个没有昵称、没有队伍的空记录，它会实打实占掉一个座位。
  因此 `normalizeRoom()` 会**忽略没有 `joinedAt` 的座位**，下一次事务写回时顺带清掉。
- ⚠️ 同一个"直写"还有一个更严重的变体：**房间在某人离线期间被删掉，他重连时这一写会把
  整个房间节点重建出来**，得到只剩 `players`、没有 `meta` 的**空壳房间**。
  它命中不了任何一条 TTL（座位非空、还有人"在线"），会永久占着那个房间码。三处一起兜：
  - `roomRelease()` 把没有 `createdAt` 的节点直接判为可释放；
  - `roomRelease()` 数人时也只数带 `joinedAt` 的座位（它读的是**原始数据**，
    `normalizeRoom` 的过滤管不到它，两边对"房间里几个人"必须给出同一个答案）；
  - `applyAction()` 把没有 `meta` 的节点当作**不存在** —— 于是它不会被 `JOIN` 接住
    （否则会变成一间没有房主、谁也开不了局的死房），但可以被 `CREATE_ROOM` 重新占用。

## 15. 音效与渲染抖动

### 音效

全程用 **WebAudio 振荡器现场合成，不引入任何音频文件**（仓库里没有可复用的音效资源，
其它小游戏引用的 `.mp3` 大多已不在部署产物里）。实现见 `sound.js`，预设覆盖
新消息 / 进出房 / 开局 / 轮到我出手 / 本轮结算 / 作废 / 获胜 / 落败 / 被移出。

- 浏览器要求先有用户手势才允许出声，所以 AudioContext 懒创建，`boot()` 时挂一次性的
  `pointerdown` / `keydown` 解锁监听。
- 顶栏常驻 🔊/🔇 开关，状态存 `localStorage.spySignalSound`（默认开）。它管的是**全部**音效，
  不只聊天。
- 触发点集中在 `main.js` 的 `announceRoomChange()`：比对前后两份房间状态，
  只对"名册增删""本轮结算产生（用 `roundResult.at` 判定，避免同一份结算被重复播）"
  "阶段推进到我需要动手"这几类真正相关的变化出声。

### 抖动

根因不是某个激烈的动画，而是**整屏 `clear()` + 重建**：`.ss-block`（60 多处）原先挂着
`animation: ss-rise`，于是"谁切了准备 / 在线状态抖一下 / 20 秒倒计时到点"都会让满屏的块
同时重播淡入 + 上移。现在的处理：

1. **删掉 `.ss-block` 与 `.ss-winner` 的进场动画**（`@keyframes ss-rise` 一并删除）。
   要保留入场感只能在"阶段变化"那一层做，不能挂在通用块上。
2. `ss-pulse` 摆幅收窄（`0.45→0.85` / `0.92→1.04`）、周期放长到 2.2s ——
   它会被重绘重置相位，摆幅大时那一下很跳。
3. **房间没变化就跳过重绘**：`main.js` 的房间回调里比对 `JSON.stringify(room)`，
   相同就不 `render()`。
4. **保留滚动位置**：`render()` 前记 `window.scrollY`，渲染后还原。
5. 聊天消息只重画聊天面板（`renderChat()`），**不碰 `#ssScreens`** —— E2E 有断言。
6. 删掉 `healthTrack()` 里给 `.ss-pip` 写的 `animationDelay`（`.ss-pip` 早已没有动画）。

> 顺带：顶栏的连接状态改成了「状态点 + 文字」，窄屏只留状态点。
> 加上音效开关按钮之后，390px 宽度下顶栏原本会把「谍报风云」「退出」挤成竖排一行一个字。
